# 0017 — tinyprobe-app, the first version

- **Status:** Approved
- **Roadmap:** M5-1
- **Repositories:** tinyprobe-app (new), tinyprobe-vscode (the run view becomes shared code). tinyprobe does not change ([decision 0004](../decisions/0004-the-app-is-a-client-of-the-cli.md)).
- **PRs:** —

## Problem

tinyprobe has two faces: the terminal and VS Code. People who use Postman to click through an API (testers, product people, support, developers in another editor) have neither. For them, `tinyprobe call api/shop.yaml get_user --with id=1` is where they go back to Postman.

What they need is small: open a folder, see its endpoints and workflows, send a request from a form, run a workflow and watch it, pick the environment, add a request without writing YAML. The binary already does the work, and its JSON protocol is enough to build on: the extension proves it, and its run view already renders the events in a browser.

## Proposal

A separate app, **tinyprobe-app**, in its own repository. A small launcher serves a page on `127.0.0.1`, opens it in the browser and runs `tinyprobe` for every call and run.

```text
Browser          the page: plain HTML, JavaScript and CSS, no framework, no build step
   ⇅  HTTP on 127.0.0.1 (the launcher's own API, internal to tinyprobe-app)
Launcher         C# Native AOT, about 2 MB: serves the page, reads and writes files in the
                 opened folders, runs tinyprobe and streams its output
   ⇅  the public contracts: YAML files, inspect --json, ndjson events, exit codes
tinyprobe        the engine, unchanged: the same binary as in CI
```

### Install and start

- **Download** the archive for your platform from the releases of tinyprobe-app (the same six platforms as the CLI) and double-click `tinyprobe-app`. Nothing to install first: no runtime, no Node, no .NET.
- **The first start** asks in the page whether to add an icon: Start menu and desktop on Windows, a `.desktop` file on Linux, a `.app` in `~/Applications` on macOS. It can be done later from the settings.
- **A console window** stays open while the app runs:

  ```text
    ⚡ tinyprobe-app 0.1.0   (tinyprobe 0.20.0)

    open   : http://127.0.0.1:4747/
    folder : /home/me/shop/tinyprobe

    tinyprobe-app is running. Close this window to stop it.
  ```

- **A second click** on the icon finds the running app and opens a new browser tab on it; it does not start a second one.
- **An app window.** In Chrome and Edge, "Install app" gives the page its own window and icon (a Progressive Web App), with nothing more to install.

### Finding tinyprobe

- The app uses the `tinyprobe` of the `PATH` when it is at least the version it needs (0.20.0 for this version).
- Otherwise it uses its own copy, in its data folder (`%LOCALAPPDATA%\tinyprobe-app` on Windows, `~/Library/Application Support/tinyprobe-app` on macOS, `~/.local/share/tinyprobe-app` on Linux).
- If there is neither, the page offers to download it: "tinyprobe 0.20.0 is needed (4 MB). Download". The download comes from the GitHub release of tinyprobe and is checked against its `SHA256SUMS`, as `install.sh` does. It uses the system's `curl` and `tar`, which ship with Windows 10 and later, macOS and Linux desktops: an HTTPS client in the launcher would make it twice as big (6.4 MB against 3.5 MB, measured). When a newer release exists, the settings offer to update the app's own copy (`tinyprobe update`); a `tinyprobe` on the `PATH` is left alone.

### What the page shows

```text
┌──────────────────────────┬──────────────────────────────────────────────────────────┐
│ shop/tinyprobe       ▾   │  get_user                         GET /api/users/${id}    │
│ env: [env.local.yaml ▾]  │                                                          │
│                          │  id *        [ 1          ]                              │
│ API                      │  verbose     [ false      ]   default                    │
│  ▾ api/shop.yaml         │                                     [ ▶ Send ]           │
│     login       POST     │ ──────────────────────────────────────────────────────── │
│   ● get_user    GET      │  ✓ get_user id=1   GET  200  12ms  /api/users/1          │
│     list_orders GET      │    Response  Request  Headers                            │
│   + New request          │    {                                                     │
│ Workflows                │      "id": 1,                                            │
│  ✓ workflows/users.yaml  │      "email": "ada@example.com"                          │
│  ✗ workflows/orders.yaml │    }                                                     │
│  ! workflows/broken.yaml │                                                          │
│ [ ▶ Run all ]            │                                                          │
└──────────────────────────┴──────────────────────────────────────────────────────────┘
```

- **Open a folder.** The first screen lists the recent folders and a folder browser (the launcher lists the directories: a browser page cannot give a path to a program). Opening a folder that has a `tinyprobe/` subfolder opens that one.
- **The folder** is listed in the left column: the API files with their endpoints, the workflows, the sequences, and the environment picker. Files are found as the extension finds them (a top-level `endpoints:`, `steps:` or `sequence:`), and their content comes from `tinyprobe inspect --json`. The main area shows a summary, **▶ Run all**, and the problems of every invalid file with `file:line:column`, as `inspect` reports them. A folder with no tinyprobe files offers to create one (below) and names the README's prompts for coding agents.
- **An endpoint** opens a form from its `inspect` document: required params first, defaults shown, then the query parameters and every other argument the environment does not define; what the environment defines (`baseUrl`, `token`) is folded away, to fill in only to override it. The method and the path are shown as written (`/api/users/${id}`: only a run resolves placeholders). Values are typed like YAML, as `--with` reads them. **▶ Send** runs `tinyprobe call` and shows the result in the run view: status, duration, headers, body, and the request as sent. The last values of each endpoint are kept in the browser.
- **A workflow** shows its steps as `inspect` lists them. **▶ Run** runs it with live results, **Run to here** on each step runs up to it (`--to`), **▶ Run all** runs the folder as a suite. The run view is the extension's: the steps, the checks of the selected one with their actual values, saved values, request and response, the items of a `for_each`.
- **The environment** is picked among the env files of the folder (`env.yaml`, `env.*.yaml`, `env-*.yaml`, `environment.yaml`, as in the extension) and passed with `-e` to every call and run. The page lists the names of its variables, without values; editing them is M5-2.
- **+ New request** opens a form: the API file (an existing one, or a new `api/<name>.yaml` with its `base_url`), the endpoint's name, method, path, the names of its query parameters (the format's `query: [page, search]`), headers, a JSON body, the auth set (from the file's `auth`), and a default for each `${...}` placeholder written in the other fields. A placeholder given a default becomes a param (typed like YAML, as `--with` reads it: `1` stays a number); the others stay free, filled by the call or the environment. **Save** adds the endpoint to the file as text, keeping its comments and order, then runs `tinyprobe inspect` on it. If the file is no longer valid, the app restores the previous text and shows the problems.
- **Files change under it.** The user may edit the YAML in an editor at the same time: the page reads the folder again when it gets the focus and before every call, run or save.

### Rules

- **The app is a client of the CLI** ([decision 0004](../decisions/0004-the-app-is-a-client-of-the-cli.md)): requests, validation and results come from `tinyprobe`; the app keeps no request, collection or variable outside the YAML files of the folder, and what it writes runs unchanged with `tinyprobe run`.
- **No state between calls** ([decision 0003](../decisions/0003-endpoints-declare-workflows-run.md)): a Send is one `call`, a Run is one `run`. Values pass between requests only through the `save` of a workflow, and the page says so where a Postman user would look for it.
- **Several runs at once** are allowed (a Send while a workflow runs), each in its own result panel. Closing a panel or the page stops its `tinyprobe` process.
- **Nothing leaves the machine** except the user's own requests and, when the user asks, the download of tinyprobe: no fonts, no CDN, no telemetry, no account.

### Security

The launcher runs requests with the credentials of the environment files and writes files, so no other web page and no other user of the machine may drive it.

- It listens on `127.0.0.1` only.
- **A session cookie.** The launcher opens the browser on `/open?t=<one-time token>`, which sets an `HttpOnly`, `SameSite=Strict` cookie and redirects to `/`. Every API request needs it. A second start asks the running app for a new one-time token, through a file only the user can read.
- `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (DNS rebinding), and requests that change something must come from the page's own `Origin`. No CORS headers are sent.
- Files are read and written only inside the opened folders, after resolving `..` and links. The files those import are the engine's business, as on the command line.
- Request and response headers are shown as sent, `Authorization` included, as in the extension: they stay in the browser.

### The repository

- `launcher/`: the C# Native AOT launcher, with no ASP.NET and no `HttpListener` (a minimal HTTP/1.1 server on sockets: 2.0 MB measured on 2026-10-30, against 6.2 MB with `HttpListener`).
- `web/`: the page. `web/shared/`: the code shared with the extension (below).
- Tests: the launcher's routes, cookie, `Host` and `Origin` checks, paths and streaming, in C#; the page's pure logic (forms, values typed like YAML, writing an endpoint into a file) with `node --test`. End to end in CI: the launcher with the released `tinyprobe`, on `docs/example` of that release, against the test server image `ghcr.io/kikutano/tinyprobe-testserver`.
- A performance guard as in the CLI: the launcher under 4 MiB, the page under 200 KiB, the start under 50 ms (measured on 2026-10-31: 3.47 MB with the page inside, 111 KB, 3 ms). The first estimate of 3 MB did not count the JSON, process and hashing code a launcher needs on top of a bare HTTP server.
- Releases: an annotated tag publishes the archives for the six platforms, with checksums. Signed installers come with M5-5.

## Validation

The launcher's own errors, in its console window and in the page:

```text
tinyprobe-app: tinyprobe 0.18.0 on the PATH is older than 0.20.0; using the app's own copy
tinyprobe-app: the download of tinyprobe 0.20.0 does not match its checksum; nothing was installed
tinyprobe-app: port 4747 is in use by another program; using 4748
```

In the page, before a Save:

```text
The name 'get user' is not valid: use letters, digits and _, e.g. get_user
This file already has an endpoint 'get_user'
```

Everything else is a problem reported by `tinyprobe inspect`, shown as it comes.

## Protocol

None in tinyprobe. The app reads `inspect --json`, the ndjson events of `run` and `call` and `tinyprobe schema` as [docs/protocol.md](../protocol.md) documents them, and ignores keys it does not know.

The HTTP API between the page and the launcher is internal to tinyprobe-app: it serves only the page shipped in the same archive, and can change in any version.

## Extension

- The run view (`media/run-view.js`, `media/run-view.css`) becomes shared code. Its canonical copy moves to tinyprobe-app (`web/shared/`), where M5-4 adds the forms; the extension copies it (`scripts/dev.sh sync-shared`), and its CI checks that the copy matches the tinyprobe-app version it names. The bootstrap that talks to VS Code stays in the extension.
- The same goes for the text editing of YAML (`src/environmentFile.js`), which the new-request form extends.
- No new `MINIMUM_VERSION`: the extension's behaviour does not change.

## Docs

- tinyprobe-app: `README.md` (download, first start, what the page does, security, how to open an unsigned app on macOS and Windows until M5-5), `CLAUDE.md` and `scripts/dev.sh` as in the other repositories.
- tinyprobe `README.md`: a short section, "The app", with a screenshot and the link.
- `ROADMAP.md`: M5-1 linked to this spec.
- `docs/llm-guide.md`: nothing; agents keep using `inspect`, `call` and `run`.

## Out of scope

- The environment editor and the request history (M5-2), the diagram of a workflow (M5-3), forms for everything else (M5-4), signed installers and package managers (M5-5).
- Importing a Postman collection in the app. The user's coding agent does it ([decision 0001](../decisions/0001-ai-does-the-import.md)); the page offers the prompt to copy, as the extension's **Migrate with AI** does.
- A desktop window of its own (Tauri, Electron). The page in the browser is the app; the same page can go into a window later without being rewritten.
- Listening on another interface, so the app runs in Docker or on a server: it needs another security model.

## Acceptance criteria

- [ ] Start from a double-click on the six platforms, the console window, a second start opening the running app, the icon offered at the first start.
- [ ] tinyprobe found on the `PATH`, too old, missing and downloaded with the checksum checked, a bad checksum refused.
- [ ] Open a folder (browser, recent folders, the `tinyprobe/` subfolder), the listing of `docs/example` with its endpoints, workflows, sequences, environments and the problems of an invalid file.
- [ ] Send an endpoint with required params, defaults and YAML-typed values; run a workflow, Run to here, Run all, with live results and `for_each` items; stop a run by closing its panel.
- [ ] + New request into an existing file and into a new one; the file keeps its comments; an invalid result restored with its problems shown; the new endpoint runs with `tinyprobe call` from a terminal.
- [ ] Security: `127.0.0.1` only, the cookie required, a wrong `Host` or `Origin` refused, a path outside the opened folders refused; tested against the running launcher.
- [ ] The tests and the performance guard above, in the CI of tinyprobe-app; the run view shared with the extension and its copy checked there.
- [ ] Docs above; `scripts/dev.sh check` passes in tinyprobe-app and in tinyprobe-vscode.

## Open questions

1. **The port.** Option A, a fixed default port (4747, the next free one if another program has it, remembered), as proposed: the app installed as a browser app opens the same address every time, and the page's remembered values (environment, last arguments) stay, since the browser keeps them per address. Option B, a free port at every start: never a conflict, but the installed browser app and the remembered values break at each start. *Recommendation: A.*
2. **Where the shared browser code lives.** Option A, in tinyprobe-app, copied into the extension, as proposed: the app is the visual project, and the forms of M5-4 are written there first. Option B, in the extension, copied into the app: the run view is already there, but the app would depend on the extension's releases. *Recommendation: A.*
3. **The icon.** Option A, the app offers it at its first start, as proposed: a download and a double-click are enough, no installer to trust. Option B, install scripts (`install.sh`, `install.ps1`) in tinyprobe-app that also add the icon: one command, but a terminal, which the people of M5 avoid. *Recommendation: A, and the install scripts too for those who prefer them.*
4. **Which tinyprobe.** Option A, the one on the `PATH` when it is new enough, else the app's own copy, as proposed: a developer's app and terminal run the same binary. Option B, always the app's own copy: the version is always the one the app was tested with, but a developer has two tinyprobes that may differ. *Recommendation: A.*
5. **A new request that makes the file invalid.** Option A, the previous text is restored and the problems are shown, as proposed: a form never leaves a broken file. Option B, the file is kept and the problems are shown, to be fixed by hand: closer to what an editor does, but it leaves the user with a file the page cannot list. *Recommendation: A.*
6. **Version numbers.** tinyprobe-app starts at 0.1.0 and follows its own SemVer, with the oldest tinyprobe it needs in its README and in the console line. *Recommendation: yes; aligning it with the CLI would force a release of the app for every release of the CLI.*
